# loomworks.nvim — Project Context for Claude

## What this is

A Neovim workspace management plugin. Provides project structure information
to other plugins (LSP configs, overseer, DAP). Non-invasive — collaborators
don't need to know it exists. Read-only toward project files.

The plugin lives at `C:/src/nvim-plugins/loomworks.nvim` and is loaded via the
owner's Neovim config (C:/Users/samie/AppData/Local/nvim, branch `loomworks`),
which auto-loads every subdirectory of `C:/src/nvim-plugins` as a lazy.nvim dev plugin.

## Philosophy

- Assistive not authoritative — helps the user, doesn't replace build systems
- Minimal config — loomworks.json only describes structure and deviations from defaults
- Modules derive everything else from existing project files (CMakeLists.txt, CMakePresets.json, build-profile.json5, etc.)
- Existing infrastructure respected — vscode tasks, overseer, CMakePresets.json reused not replaced
- One active workspace at a time — set from cwd at startup or via explicit API call
- Opening files outside workspace doesn't change the active workspace

## Terminology

- **workspace** — top-level unit, defined by `loomworks.json`
- **project** — sub-component with a type (cmake, ets, typescript, etc.)
- **module** — Lua handler for a project type
- **configuration** — build variant within a project (Debug, Release, ohos-debug)
- **compiler** — auto-detected toolchain, selected orthogonally from configuration in UI
- **configuration_set** — named grouping tying configurations across projects (debug, release)

## Three-File Model

**`loomworks.json`** — intent. What projects exist and how configured. User chooses
whether to commit it. Purely declarative — describes what's available, not state.

**`.nvim/loomworks.user.json`** — user preferences only. Small, stable, written only
on explicit user action: active configuration set, compiler selection per project,
default task (F5 target), named toolchain definitions (machine-local paths).

**`.nvim/loomworks.cache.json`** — reality. Sparse record of what has actually been
configured/built. Only contains entries for things that have happened. Never
auto-removes entries — survives git branch switches intact. Grows as builds happen.

```json
{
  "_meta": { "version": 1, "loomworks_hash": "abc123", "cached_at": "..." },
  "configured": {
    "ScenePluginAddon": {
      "type": "cmake",
      "cmake": {
        "Debug x gcc-11.4": {
          "state": "built",
          "build_dir": ".nvim/build/ScenePluginAddon/Debug",
          "targets": {
            "scene_runner": { "type": "executable", "built": true, "last_built": "..." }
          },
          "last_configured": "...",
          "last_built": "..."
        }
      }
    }
  }
}
```

Status page reconciles all three sources:
- In config + in cache → normal, show state
- In config, not in cache → available, never configured
- In cache, not in config → orphaned (shown distinctly, listed at end, user cleans manually)

All files: atomic writes (temp + fsync + rename), one .bak generation,
JSON + schema validation on read, fall back to .bak on failure, version field
in `_meta` for migration handling.

## loomworks.json Schema

```json
{
  "name": "LumeTS",
  "projects": {
    "ScenePluginAddon": { "cmake": {} },
    "NativeDemo":       { "ets": {}   },
    "ScenePluginTest":  { "typescript": {} }
  },
  "configuration_sets": {
    "debug":   { "ScenePluginAddon": "Debug",   "ScenePluginTest": "development", "NativeDemo": "debug"   },
    "release": { "ScenePluginAddon": "Release",  "ScenePluginTest": "production",  "NativeDemo": "release" }
  }
}
```

Key schema decisions:
- Dict with path as key (not array with name field)
- Type implicit from inner key (`"cmake": {}` not `"type": "cmake"`)
- `name` optional — falls back to workspace root directory name
- `path` field on project defaults to the key — only needed when folder name differs
- `configuration_sets` auto-generated by lowercase name-matching when not declared
- `"depends_on": []` reserved as a schema stub for future cross-project dependency ordering

With overrides:
```json
"ScenePluginAddon": {
  "cmake": {
    "configurations": {
      "Debug":      {},
      "Release":    {},
      "ohos-debug": { "toolchain": "${OHOS_NDK_HOME}/cmake/ohos.toolchain.cmake" }
    },
    "compile_commands_from": "ninja-debug"
  }
}
```

`compile_commands_from`: a configuration can source compile_commands.json from another
configuration (e.g. MSVC build + Ninja companion for clangd). The companion config can
have `"role": "compile_commands"` to hide it from UI.

**Toolchain path rules:**
- `${ENV_VAR}/relative/path` — env var expanded at runtime; error if unset when config is selected
- Relative path from workspace root — always allowed
- `@name` — named toolchain defined in `.nvim/loomworks.user.json` (reserved for future)
- Absolute paths — **forbidden** in loomworks.json (breaks on other machines)

## Module Interface

```lua
{
  id = "cmake",

  -- Check if the path+config is valid; return warnings for non-fatal issues.
  validate = function(path, config) → { valid, warnings[] } end,

  -- Return what the module knows about the project from its own files.
  -- compilers NOT returned here — that's a core concern (loomworks/compilers.lua).
  -- targets only present if cmake File API data exists (post-configure).
  info = function(path, config) → {
    configurations = {
      ["Debug"]      = { generator = "Ninja", toolchain_locked = false },
      ["ohos-debug"] = { generator = "Ninja", toolchain_locked = true,
                         toolchain = "${OHOS_NDK_HOME}/cmake/ohos.toolchain.cmake" },
    },
    targets = {           -- only after configure
      ["scene_runner"] = { type = "executable", output = "..." },
    },
  } end,

  -- Return overseer task templates for a project in a given active configuration.
  -- env field carries any toolchain/compiler environment the task needs.
  tasks = function(project, active_config) → {
    { template = { name = "...", builder = ... }, env = { OHOS_NDK_HOME = "..." } },
  } end,

  -- Compare the current config/files against what's in the cache.
  -- Hash check in core is a fast pre-filter; if hash differs, inspect() is called.
  -- Distinguish significant changes (needs_refresh=true) from trivial notes.
  inspect = function(path, config, cached) → { needs_refresh, reasons[], notes[] } end,

  -- Future (interface defined now, not implemented in v1):
  debug_configs = function(project, active_config) → { dap_config, ... } end,
  tests         = function(path, config, active_config) → { runner, ... } end,
}
```

## Shared Compiler Detection (`loomworks/compilers.lua`)

Shared by cmake, meson, and any other module that needs compiler info.
cmake and meson do NOT implement their own detection.

```lua
-- loomworks/compilers.lua
{
  -- lang: "c_cpp" (others future: "rust", etc.)
  -- Returns detected compilers with environment needed to use each.
  detect = function(lang) → {
    { id = "gcc-12.3.0", name = "GCC 12.3.0", path = "/usr/bin/gcc-12", env = {} },
    { id = "clang-17.0", name = "Clang 17.0",  path = "/usr/bin/clang-17", env = {} },
    -- Windows: vswhere.exe → vcvarsall.bat environment capture
    { id = "msvc-2022-17.8", name = "MSVC 2022 17.8", env = { VCToolsInstallDir = "..." } },
  } end,
}
```

Compiler selection is ORTHOGONAL to configuration:
- Non-toolchain-locked configs → user picks configuration × compiler in UI
- Toolchain-locked configs → compiler implicit from toolchain, no selection shown
- Only one set active at a time — stored in loomworks.user.json

## CMakePresets Integration

- cmake module reads `CMakePresets.json` + `CMakeUserPresets.json` (with full inheritance)
- Each configure preset becomes a loomworks configuration; uses preset's `binaryDir`
- Auto-generates Debug/Release/RelWithDebInfo **only if no presets define configurations**
- `loomworks.json` `configurations` block adds or overrides on top of preset-derived ones
- Preset's `toolchainFile` maps to the `toolchain_locked` concept in module info

## Configuration State Machine

States: `unconfigured → configured → built → stale → built`
        `any → failed_configure` (never auto-clean)
        `configured → failed_build` (never auto-clean)

Rules:
- Never auto-clean failed states (rebuilding large C++ is expensive)
- Only clean on explicit user request
- `last_configured` and `last_built` stored separately (failed build ≠ invalid configure)
- For multi-config generators (MSVC, Ninja Multi-Config), configured state shared across configs sharing build dir
- If config has `compile_commands_from`, referenced config must be at least configured
- `state` on a configuration = overall; per-target `built` bool is additive info for UI

## Project Status Model

`status` enum (purely build state, no module-specific values):
- `unconfigured`     — nothing in cache for this project
- `configured`       — configure succeeded, not yet built
- `built`            — built successfully
- `failed_configure` — configure attempted and failed
- `failed_build`     — configure ok, build failed

Separate flags (orthogonal to status):
- `orphaned`         — in cache, not in current config (listed at end of projects)
- `needs_refresh`    — config diverges from cache (module's `inspect()` determines this)
- `refresh_reasons`  — list of strings from module explaining what changed

System remains functional regardless of flags. They are informational only.
Refresh is always user-triggered, never forced.

Hash check in `_meta` is a fast pre-filter. If hash matches → skip module inspection.
If hash differs → call each module's `inspect()` to find what changed and why.

## Core API

```lua
-- Primary consumer API
loomworks.get_active_configuration_set()  -- merged projection of active set
loomworks.on('active_set_changed', fn)    -- signal, passes new data as argument

-- Full data (for status page, advanced consumers)
loomworks.get_workspace()
loomworks.on('workspace_changed', fn)

-- Computed helpers
loomworks.project_for_buf(bufnr)          -- path-prefix matching, returns active project slice

-- Workspace management
loomworks.setup({ root = path })
loomworks.set_workspace_dir(path)
loomworks.activate_set(name)
loomworks.set_default_task(project, target)
```

`get_active_configuration_set()` merges all three files — consumers never touch
individual files. Merge order: config (intent) + user (choices) + cache (reality,
wins for configured projects). Orphaned projects at end of list.

```lua
{
  name = "debug",
  projects = {
    ScenePluginAddon = {
      type = "cmake", configuration = "Debug", compiler = "gcc-11.4",
      status = "built", orphaned = false, needs_refresh = false,
      cmake = { compile_commands = "...", targets = { scene_runner = { type = "executable", built = true } } },
    },
    OldProject = {                          -- orphaned, at end
      type = "cmake", status = "built", orphaned = true,
      refresh_reasons = { "not in current loomworks.json" },
    },
  },
}
```

Signal passes data directly — no need to re-call, no race condition.

## Overseer Integration

Register as overseer template provider (not direct injection):
- Tasks generated in-memory at workspace load, never written to .vscode/tasks.json
- Existing .vscode/tasks.json read natively by overseer — not touched by loomworks
- cmake module auto-generates: "ScenePluginAddon: configure Debug", "build Debug x gcc-11.4"
- F5 resolves `default_task` to concrete overseer task via active configuration set

## :WorkspaceInfo UI

Two-level folding. Configuration sets are primary focus.
`<CR>` to fold/unfold, `<Tab>` to jump between sections.
Shows build status for ALL configs, not just active.
Shows `last_configured` and `last_built` separately when in failed state.
Shows per-target built status after configure.

**V1 modules:**
- `cmake` — full implementation
- `ets` — shim (shows project exists, no build functionality)
- `typescript` — shim (shows project exists, no build functionality)

**Implementation order:**
1. Plugin skeleton + workspace root detection (`loomworks/workspace.lua`)
2. `loomworks.json` parsing + three-file read/write with atomic writes (`loomworks/io.lua`, `loomworks/config.lua`, `loomworks/user.lua`, `loomworks/cache.lua`)
3. Module interface + cmake module (`loomworks/modules/cmake.lua`) + shims
4. Core API + merge logic + event system (`loomworks/merge.lua`, `loomworks/events.lua`, `loomworks/init.lua`)
5. `:WorkspaceInfo` window (`loomworks/ui/status.lua`)
6. clangd integration (compile_commands.json feeding)
7. Overseer template provider + F5 default task

## Key Design Decisions to Remember

- `depends_on` stub in schema — leave `[]` reserved, ignored by v1 logic
- CMakePresets: presets first, loomworks.json augments/overrides, preset's binaryDir wins
- Compilers: shared `compilers.lua`, NOT per-module; MSVC via vswhere.exe + vcvarsall env capture
- Toolchain paths: `${ENV_VAR}` expansion only in loomworks.json, no absolute paths
- `@name` toolchain references: reserved prefix for future named toolchains in user.json
- Target-level `built` tracking in cache (separate from configuration-level `state`)
- clangd auto-reloads when compile_commands.json changes on disk — no explicit restart needed
- Atomic writes on Windows: rename can fail if file is open; implement retry with short sleep
